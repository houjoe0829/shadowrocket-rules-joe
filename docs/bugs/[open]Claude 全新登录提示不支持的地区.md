## 问题描述
在 Shadowrocket 代理下，发起**全新登录** Claude 时提示「不支持的国家或地区」。已登录的会话不受影响，可以正常使用。
最初以为是 Claude 桌面端特有的问题，后经无痕窗口验证，与客户端无关。

## 环境
| 项目 | 值 |
|---|---|
| 代理 | Shadowrocket for Mac，隧道模式（MacPacketTunnel），已开启强制路由 |
| 配置 | shadowrocket-rules-simplified.conf（极简版） |
| 对照工具 | QuantumultX，**相同节点池**，同样的登录操作正常 |
| 系统 | macOS，`AppleLocale=zh_CN`，时区 `Asia/Shanghai`，**无公网 IPv6** |
| 机场节点 | `155.254.102.168`，按端口区分不同地区 |

## 一、已做的尝试
### 假设 1：节点在香港，属于 Anthropic 不支持地区
查证 Anthropic 官方支持列表：日本、新加坡、韩国、台湾、美国均支持；香港、澳门、中国大陆不支持。
**结论：方向对，但不是本例主因。** 实测当前出口并非香港。

### 假设 2：Claude 桌面端（Electron）绕过了代理
用 `lsof` 检查 Claude.app 全部进程的 TCP 连接，发现 `Claude 198.18.0.1:53165->198.18.0.80:443`，`198.18.0.80` 正是 curl 解析 `claude.ai` 得到的 fake-IP。
**结论：证伪。** 桌面端完整走隧道，未绕过代理。

### 假设 3：登录链路上有域名没被规则覆盖
从 Claude.app 包内提取出登录地址为 `https://claude.com/cai/oauth/authorize`，实测 307 跳转至 `https://claude.ai/oauth/authorize`，Google 登录走 `accounts.google.com`。
逐一比对规则，`claude.com`、`claude.ai`、`google.com` 全部命中「AI 服务」。
**结论：证伪。** 规则无遗漏。

### 假设 4：Safari 的 iCloud 私人中继绕过代理
GitHub issue 27741 证实桌面端 Google 登录会强制拉起 Safari 而非默认浏览器（已被官方 close as not planned）。本机 `com.apple.networkserviceproxy` 确实存在配置，`NSPLastGeohash=wt3n`。
用 AppleScript 驱动 Safari 访问 `claude.ai/cdn-cgi/trace`，结果与 curl 完全一致（同一 SG 出口、`warp=off`）。
**结论：证伪。** 私人中继未生效，Safari 与 curl 走同一条路。

### 假设 5：Shadowrocket 用 IPv6 连接节点，落到了不同入口
检查 MacPacketTunnel 的全部对外连接，均为 IPv4（`155.254.102.168:端口`），无一条 IPv6；本机也没有公网 IPv6 地址。
**结论：证伪。** IPv6 完全产生于节点侧，与本地无关。

### 假设 6：出口 IP 信誉问题（机房/VPN 段被拦）
未能证实。curl 访问登录页被 Cloudflare「Just a moment」人机验证挡住，无法从命令行读到真实报错页。
改用 Safari 渲染 `claude.ai/login`，页面完整正常，无任何地区报错——说明拦截不发生在访问登录页时，而在更靠后的登录环节。

### 关键验证：无痕窗口全新登录
在日常使用的浏览器中开无痕窗口，走完 Google 登录，**成功复现**「不支持的地区」。
**结论：问题与客户端无关，是「全新登录」这个动作本身过不了校验。** 此前「浏览器能正常使用」只证明旧 session cookie 有效，地区校验仅在登录时执行一次。

## 二、已确认的结论
1. **与 Claude 桌面端无关。** 桌面端只是必须走全新登录，才第一个撞上该问题。
2. **与域名分流规则无关。** 登录链路全部域名均正确命中「AI 服务」。
3. **地区校验只在登录时执行。** 已有会话不会被重新校验，这解释了「网页版能用但登录失败」的表象。
4. **`api.anthropic.com` 无地区闸门**（无凭证访问返回 401），而 `claude.ai` 网页有。这解释了为何 Claude Code CLI 始终正常。
5. **机场节点是双栈，且 IPv4 与 IPv6 归属地不一致：**

| 策略 | IPv4 出口 | IPv6 出口 | IPv6 稳定性 |
|---|---|---|---|
| 美国节点 | `155.254.126.10` US | `2602:fa4f::/32` SG | **每请求轮换** |
| 默认 PROXY（日本） | `185.220.238.68` JP | `2602:ffe4:8:521d::` HK | 固定 |

6. **`claude.ai` 会走节点的 IPv6 出口。** 因其有 AAAA 记录（`2607:6bc0::10`），节点优先选用 IPv6。而 `claude.com` 的 AAAA 是被污染的 Teredo 地址（`2001::9f6a:794b`），节点尝试失败后回退 IPv4，故出口为美国。
7. **本地无法强制节点走 IPv4。** Shadowrocket 对走代理的域名采用远程 DNS，把域名原样交给节点解析；`ipv6 = false` 只约束「本机→节点」这一段。用 `curl --resolve` 强制 IPv4 字面量也无效，因 Shadowrocket 会嗅探 TLS SNI 后仍按域名转发。
8. **顺带发现：默认 PROXY 节点连 Cloudflare 时出口在香港。** 影响面远大于 Claude——所有 Cloudflare 托管站点都会将该用户识别为香港。

## 四、尚未解释的问题
### 为什么新加坡出口也会被拒
新加坡在 Anthropic 支持列表内，理论上不该报「不支持的地区」。
目前的推测是**拦的不是国家，而是 IP 类型**：`2602:fa4f::/32` 每个请求换一个地址，是典型的机房代理池特征，可能被判定为 VPN 而拒绝，报错文案则笼统地归为地区问题。
**此推测在本例中尚未直接证实**，因 Cloudflare 人机验证阻断了从命令行抓取真实报错页。但已获外部案例旁证，详见第五节——社区普遍报告「IPv4 与 IPv6 出口不一致」「机房 IP 段」会触发 Anthropic 风控，与本例观测到的轮换 IPv6 池吻合。

### 为什么 QX 用同一节点池却正常
已定位到两处配置差异，但尚未确认哪一处（或是否两处共同）导致差异：

**差异 A —— 选点方式不同**
```
QX:            static=AI策略, 手动选择, 自动选择, 香港, ...
                              ↑ 首位是手动钉死的单台服务器
Shadowrocket:  AI 服务 = select,美国节点,...
                              ↑ url-test 分组，每小时自动挑延迟最低的
```
同一节点池，一个钉死、一个自动漂移，选中不同服务器属于正常现象。

**差异 B —— 地区正则缺少互斥条件**
```
QX 美国:  (?=.*(美|美国|US)) + 排除 香港|台湾|日本|新加坡|韩国|SG|JP|KR|HK|TW|台灣|韓國
SR 美国:  (?=.*(US|USA|America|america|us|United States|美国|...|美|美西))
          + 仅排除 海外用户专用|套餐到期|到期时间|剩余流量|expire|官网|官方|重置
```
Shadowrocket 侧完全没有地区互斥，且匹配词含裸小写子串 `us`，会误匹配 `Australia`、`Russia`、`Austria` 等节点名。其余地区分组同样存在此问题：日本用了 `jp`、韩国用了 `kr`、新加坡用了 `sg`。

## 五、外部案例佐证
经检索，本问题属于**已知问题类别**，社区已有多例记录，核心共识为「IPv4 与 IPv6 出口不一致会触发 Anthropic 风控」。

### 完全同类的报错
smartdns [issue #2388](https://github.com/pymumu/smartdns/issues/2388) 报告了几乎相同的现象：因 IPv6 链路存在，登录时收到 `App Unavailable — Claude is only available in certain regions right now`。该用户尝试用 `domain-rules /claude.ai/ -address #6` 屏蔽 AAAA 结果，**配置未生效**，nslookup 仍返回 IPv6，issue 至今无结论。
**与本例的区别**：该用户的 IPv6 来自本机（家中开了 IPv6 供 NAS 使用），本例本机无公网 IPv6，IPv6 完全产生于节点侧。因此其「本地屏蔽 AAAA」的思路对本例不适用。

### 直接印证本例机制的论述
以下引自检索到的资料：
- 「IPv6 是 Claude Code 代理环境里最常见的隐形问题，**代理客户端可能显示请求正常，但服务端同时可能看到另一条 IPv6 路径**」
- 「**IPv6 和 IPv4 可能走了不同的出口，导致账号被风控标红**」
- 「很多人其实不是在故意切 IP，而是因为家里宽带 IPv4 动态重拨、**机场节点做了负载均衡**、或者 **IPv6 和 IPv4 走了不同的出口**」
- 「Claude 的域名应该单独写一组分流规则，不要和其他服务混在一起，以确保所有相关流量走同一个出口，防止地区识别混乱」
- 「Claude AI 能识别机房 IP 段，封锁率更高」，推荐使用住宅或 ISP 代理而非机房 IP

第三条与本例完全对应：出口 IPv6 为 `2602:fa4f::/32` 轮换池，正是负载均衡特征。

### 一条需要警惕的风险
资料提到出口不一致不仅导致登录失败，还可能**触发账号风控、要求身份验证**。若反复用不合格的出口尝试登录，风险会累积。建议在确认出口合格前，减少重复登录尝试。

### 关于 Shadowrocket 的 [Host] 方案
检索到的 Shadowrocket 解法是「为**节点域名**在 `[Host]` 段指定 IPv4，或关闭节点域名的 IPv6 解析」。
**本例不适用**：本例节点本身即为 IP（`155.254.102.168`）而非域名，且「本机→节点」这一段已确认全部走 IPv4。需要控制的是「节点→Claude」那一段，本地配置无法干预。

## 六、下一步值得排查的方向
按优先级排列。

### 1. 确认两个客户端实际选中的服务器（最高优先级）
- 在 Shadowrocket 中查看「美国节点」分组当前选中的服务器名
- 在 QX 中查看「手动选择」钉住的服务器名
若两者不同，把 Shadowrocket 的「AI 服务」直接指向 QX 那台已验证可用的服务器即可，无需逐台试错。
若两者**相同**却结果不同，则说明是客户端行为差异，本文档所有基于选点的推断都需推翻重来。

### 2. 修正地区分组正则
对齐 QX 写法：补上地区互斥条件，移除 `us` / `jp` / `kr` / `sg` 这类裸小写子串。
属于独立的纯 Bug 修复，无论是否与本问题相关都应处理。

### 3. 验证「IP 信誉」推测
需要绕过 Cloudflare 人机验证抓到真实报错页。可行路径是在浏览器中打开开发者工具，走一次无痕登录，记录返回该错误的具体请求 URL 与响应体。
拿到确切的错误码或字段后，才能判断 Anthropic 拦的究竟是国家、IP 类型，还是别的信号。

### 4. 考虑把「AI 服务」改为固定单节点
`url-test` 自动分组每小时可能漂到不同服务器，导致问题时好时坏、难以复现。改为钉死单台可消除这个变量。
属于使用习惯变更，需用户确认。

### 5. 评估机场质量
该节点池存在两个客观缺陷：美国节点的 IPv6 出口为轮换池、日本节点的 IPv6 出口落在香港。二者均非配置可修复，若排查后确认是节点侧问题，需向机场反馈或更换服务商。
